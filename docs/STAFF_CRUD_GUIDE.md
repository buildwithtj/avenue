# Staff app: what you can create, edit and archive (P7/P8)

Written 23 Nov 2026 for Flavors staff and the developer. **Built locally only**: generated by `apps/staff-powerapps/gen.py`, checked by `check.py`; nothing below has been pasted into Power Apps Studio, run, or tested. Items marked [PROPOSED] are engineering choices, not client decisions. Source plan: [REDESIGN_AND_ADMIN_CRUD_PLAN.md](REDESIGN_AND_ADMIN_CRUD_PLAN.md) §5–§7.

Ground rules the screens follow: members, bookings, the hours ledger, documents, check-ins and invoices are **never deleted** (deactivate, archive or counter-adjust instead); every write shows a success or error message, and changes to members, applications and cases record who and when. The **Permissions** switches (AvenueStaffCapabilities) now hide the matching buttons, but that is a convenience only: SharePoint permissions and the flows are the real protection (Q-15). With no row for your e-mail every button shows; the owner always sees everything.

## 2. Onboarding end to end (R1)

| Stage (pipeline column) | What happens | Who / where |
|---|---|---|
| **Applied** | Application created with *Payment pending*: portal Join or public `/join` (host, test mode), or staff **New application** (goes straight to *Invite needed*) | Member, or staff in Applicants |
| **Paid / skipped** | Stripe payment confirmed, or skipped in test mode (`PAYMENTS_REQUIRED=0`); stage *Paid* / *Invite needed* until the invite is sent | Host webhook |
| **Invited** | A SharePoint admin sends the guest invitation and adds the person to *Avenue Members* (manual until Q-M3); staff tick **Invite sent**, **Invite accepted**, **In Members group** and press *Invite sent: to onboarding*. Portal applicants are already signed in and skip this column | SharePoint admin + staff |
| **Documents** | Member uploads documents (or staff upload on their behalf in Member admin > Documents); the pipeline card and the Approve row show **N of M** required documents | Member / staff |
| **Approved** | **Approve**: creates the member row as *Onboarding* if it is missing, otherwise sets the member *Active* and the application *Active*. Approval does not yet require all documents (Q-05, Q-11) | Staff |
| **Active** | The membership-card flow grants the member their card; they can book | Flow |

Test it with `gaptest-` e-mails on applications and remove the rows by id afterwards (never bulk delete). A pipeline section for docs/TEST_CHECKLIST.md is still to be written.

## 3. Manual deploy steps (developer; ask before each outward-facing step)

Nothing here has been done. Order matters.

1. **Lists** (`schema/lists.v2.json`; provision with `schema/provision.mjs` or by hand, permissions per DATA_AND_ACCESS.md §1):
   - New: `AvenueSupportCategories` (catalog), `AvenueSupportFiles` (private library), `AvenueMyDocuments`, `AvenueMyHours`, `AvenueMyBookings` (private; rows granted per member by flows). (`AvenueNoticeReads` belongs to P3.)
   - Changed: `AvenueApplicants` (Source choice **Staff**; Boolean `InviteSent`, `InviteAccepted`, `GroupAdded`); `AvenueSupportCases` (Status choice **Archived**; `ArchivedBy` Text, `ArchivedAt` DateTime); `AvenueEquipment.Category` already has Fridge in the schema — confirm the live choice.
   - **Category Choice → Text** on `AvenueSupportMessages` and `AvenueSupportCases`: first on a `gaptest-` copy, check existing values survive, then the real lists. Do this before the support flow change (R1).
   - Seed the 5 topics: `node schema/seed.print.mjs` → paste into `schema/seed.browser.js` → `seedRun()` (topics are upserted by title and never removed by `seedCleanup()`).
2. **Flows** (`flows/expressions.md`, "Redesign flows", re-read the live Code view of every live flow first): R1 + R2 on *Support message to case* (category from the list, trigger on created-or-modified with empty Outcome, attachments to AvenueSupportFiles); R9 on *Support reply to echo*; R8 on the Events/Storage decision echoes; new R4 *My documents mirror*, R5 *My hours mirror*, R6 *My bookings mirror*. R3 (owner delete) waits for Q-R5. Check each flow's run history after the first test.
3. **Host** (optional, [PROPOSED]): a read-only bridge flow on `AvenuePlans` and `SP_BRIDGE_PLANS` in `/etc/avenue/host.env`; Stripe test prices with lookup keys `avenue-<plan id>-bank|card` for any new plan. Without it the host keeps using `plans.mjs`.
4. **Staff app data sources** (Studio > Data > SharePoint `/sites/Avenue`): add `AvenueSupportCategories`, `AvenueSupportFiles`, `AvenueSupportMessages`, `AvenueDocumentSubmissions`, `AvenueDiningTables`, `AvenueTeamMembers` (plus the existing ones).
5. **Screens** (`cd apps/staff-powerapps && python3 gen.py && python3 check.py`; for each screen: clear the canvas, paste the file). Order: `setup`, `notices`, `checklist`, `support`, `events`, `storage`, `applicants`, then a **new blank screen renamed Screen23** with `memberadmin.pa.yaml`, then `more` (its new card points at Screen23). Do not paste members, compliance or payments (unchanged).
6. **Member admin form** (once, in Studio): select `maDocForm` → Edit fields → add **Attachments**; on its attachment control set *Max attachments* = 5 and *Max attachment size* = 10 (MB). If Studio rejects `Form@2.4.4` on paste, insert an Edit form named `maDocForm` by hand and copy the properties from the YAML (DataSource, Item `varMaDoc`, DefaultMode Edit, OnSuccess, OnFailure, Visible).
7. Publish the app, then test with `gaptest-` rows (one member, one application, one support message with an attachment, one document on behalf) and remove them by id.
