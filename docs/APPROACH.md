# Approach: how Avenue Phase 1 is built and shipped

Written 14 Nov 2026. See [ARCHITECTURE.svg](ARCHITECTURE.svg) (white = built, red = not built) and [SCHEMA.md](SCHEMA.md). Scope: Phase 1 only, pilot at Flavors Culinary Hub Hyattsville; owned and operated by B Street HQ.

## 1. Principles
1. **Authorise at the data, never in the UI.** Members write only to own-items intake lists; identity is the item author. The UI is never a security boundary.
2. **Flows re-validate everything.** Power Automate (`automations@`) re-checks each intake item, writes the private authoritative lists, and echoes a display-only `Outcome` to the member's own item.
3. **Fail closed.** Unknown, malformed or unauthorised input is refused with a plain-language outcome.
4. **SharePoint holds the data.** No replacement database. A small trusted server holds only what SharePoint cannot: Stripe signature checks, secrets, and event de-duplication.
5. **Money safety.** Stripe is test mode only until the client approves the demonstrated flow (STR-06). No secret appears in source, docs, logs or chat.
6. **No invented rules.** Billing cut-offs, retention, cancellation edge cases and licence coverage stay UNKNOWN and become questions.

## 3. Build method
- One developer; small host-independent reference modules (`billing-core`, `sensors-core`, `domain-core`, `integration-host`) with `node --test`, no dependencies.
- The portal is built with heft; tests run inside `npm run build` (120 tests). Staff screens are generated by `gen.py` and validated by `check.py`.
- Real site, no test environment: tests use `gaptest-` ids removed by explicit id; seed data uses `demo-` and is removed only by `seedCleanup()`.
- Independent read-only audits before release; every fix gets a test where logic changed.

## 4. Release method (build, release, deploy)
1. **Build** everything and run all suites.
2. **Release:** pick modules in `release/release.json`; the member build and `gen.py` include only those.
3. **Deploy:** the developer uploads the `.sppkg` and pastes/publishes the staff screens. Nothing reaches the client automatically. Rollback = deploy the previous package.
Waves (two modules at a time) and demo scripts: [RELEASE_PLAN.md](RELEASE_PLAN.md), [DEMO_SCRIPTS.md](DEMO_SCRIPTS.md).

## 5. Order of the remaining work
1. Developer-only: finish [CHECKLIST.md](CHECKLIST.md) (staff upload on behalf, server client wrappers, browser tests, live re-tests, cleanup).
2. Needs the developer's approval: renewal-reminder flow, failure alerts (both send e-mail).
3. Needs admin: app catalog, guest sharing, client sign-ins, privacy test with a second account.
4. Needs the client: prices (Q-04), billing rules (Q-06, Q-07), checklist and document lists (Q-10, Q-11), sensor details (Q-12).
5. Needs DKD: Stripe platform access and the host (Q-01, Q-02). Then the test-mode end-to-end, then client approval (STR-06), then live.
